## 0. Summary

Mid-train is not a scaled-up version of post-train, nor is it simply running pretrain for a bit longer. This piece adopts a conservative engineering definition:

> Mid-train is a controlled continuation of training after base pretraining and before post-train (SFT/RL, etc.), used to change the model's capability distribution, its ability to adapt to context, and the trainability that subsequent SFT/RL can exploit.

In public materials, OLMo 2 explicitly labels the stage after base pretraining and before post-training as mid-training; Qwen3, DeepSeek-V3, Llama 3, Qwen2.5-1M, and other reports don't always use this term, instead calling it pre-training, continued pre-training, context extension, or long-context pre-training. This piece groups these stages into a "mid-train-like" category only in an engineering sense — this should not be equated with the original reports' terminology.

In practice, a new team should not chase large-scale training first. Instead it should start with small-model ablations, data-bucket validation, contamination checks, and base regression evaluation, then use short-run training on the target model to validate direction, and finally use a fixed post-train recipe to check whether the gains survive. The success criterion for mid-train is not that some base benchmark goes up — it's that capability improves, forgetting stays controlled, and the gains still exist after post-train.

As for boundaries, this piece does not treat all continued pretraining as mid-train, nor does it lump inference- or architecture-level tricks like DCA, YaRN, sparse attention, or chunked prefill in with training recipes. Public cases can only serve as design references — they should not be copied directly as recipes.

The data ratios, token budgets, 90-day roadmap, quality gates, and incident runbook in this piece are all engineering starting-point suggestions aimed at new teams — they are not general conclusions handed down directly by any public paper.

For a foundation model team with post-train experience that is about to take on mid-train, the most important thing is not to jump straight into large-scale training, but to first establish four things:

1. Clarify the target capability and the non-negotiable capabilities: for example, a math improvement must not come at the cost of significant regression in general conversation, factual knowledge, or multilingual ability.
2. Run small-model and short-run ablations: first validate data buckets, learning rate, sequence length, contamination control, and forgetting risk.
3. Build mid-train-specific evaluation: you cannot look only at pretrain loss, nor only at the leaderboard after post-train.
4. Let the Post-train DRI pick up the baton to validate: one of mid-train's success criteria is that gains still hold after SFT/RL and that training becomes more controllable — not just that the base checkpoint scores better on a handful of zero-shot metrics.

### 0.1 Reader decision tree: which kind of mid-train should you actually do

| Goal | Priority path | First-round experiment | Key evaluation | Not recommended to start with |
| --- | --- | --- | --- | --- |
| Math, code, STEM, complex QA | Capability mid-train | Small-model data mix + low-LR short run | Target capability gain + general-capability regression | Simultaneously extending to 128K/1M |
| 32K/128K long context | Context extension | Gradual length extension + long-document data buckets | Multi-evidence, long-document, long-code tasks | Looking only at needle-in-a-haystack |
| RL reasoning ceiling | Reasoning substrate mid-train | Verify whether base already has edge-of-competence | Fixed RL/RLVR recipe comparison as a follow-up | Treating RL itself as the source of capability |
| Vertical-domain capability | Domain continued pretraining | Low-proportion domain data + general-fidelity data | Domain tasks + general regression | Saturating training with a single domain corpus |
| Coding agent / tool use | Code/FIM/trajectory mid-train | FIM, repo-level completion, multi-file localization | repo tasks, editing tasks, post-train agent eval | Moving all interaction formats forward into mid-train |

This decision tree is an entry point for execution, not an exclusive taxonomy. A mature project may ultimately include capability shaping, long-context adaptation, and post-train readiness all at once, but the first round should validate only one primary hypothesis.

### 0.2 What to do on day one

If you're launching a mid-train project today, don't start training first. Day one should be just 7 things:

1. Align the DRIs for Model, Data, Training Infra, Eval, Post-train, Safety/Compliance, and Product/Domain.
2. Write a one-page Mid-train charter: target capability, non-negotiable capabilities, why this must be done in mid-train, budget boundaries.
3. Freeze the v0 owner and schema of the eval registry; before training, freeze the v1 eval registry, including base eval, specialized eval, long-context eval, private holdout, and manual sample review. Without v1, you don't enter Gate 1.
4. Have the Post-train DRI freeze the v0 owner and schema of the paired protocol; before training, freeze the v1 paired protocol, including SFT/RL data version, training budget, seed, harness, eval sets, and failure criteria.
5. Create the experiment-ledger schema, and rule that experiments without a ledger entry cannot be used as the basis for conclusions.
6. Define the pass conditions, block conditions, and sign-off owners for Gates 0-5.
7. Make explicit what must not be done in week one: don't tune parameters while looking at private holdout, don't change mix/filters/eval versions under the same experiment ID, and don't treat proxy success as guaranteeing target-model success.

## 1. Terminology boundary: what is mid-train

### 1.1 A working definition

This piece adopts an engineering definition rather than a terminology-purist one:

> Mid-train is the continued-training stage after base pretrain and before post-train. It still primarily uses a language-modeling objective or a variant of it, but the data, learning rate, sequence length, and capability targets have already shifted from "maximum coverage of world text" to "high-quality capability shaping."

This definition covers several kinds of public practice:

- late-stage pretraining / annealing: continuing training at a lower learning rate on high-quality data, pursuing lower loss and stronger downstream capability.
- domain / capability continued pretraining: continued training around capabilities such as code, math, STEM, medicine, law, finance, or multilinguality.
- long-context extension: extending from the original base context to 32K, 128K, 256K, etc., paired with position encoding, attention optimization, and long-document data; if the goal is 1M-scale context, training length, position/attention extrapolation, chunked prefill, KV cache, and serving cost should be validated separately — this should not be written up as plain continued training or a data recipe.
- reasoning-oriented mid-train: using math, code, synthetic reasoning, textbook-style data, QA/CoT, etc. to make the base model more suitable for subsequent RL or RLVR.

Mid-train overlaps with continued pretraining, but they emphasize different things: continued pretraining describes "where training picks up from"; mid-train emphasizes more "why we're running it, what data is shaping it, and how it serves post-train."

### 1.2 Division of labor with post-train

Post-train teams easily think of mid-train as "more SFT data" or "SFT a little earlier." This is dangerous, because the two optimize for different things.

Mid-train cares about:

- Whether the model internally has the knowledge, algorithmic patterns, and representational capacity needed to solve problems.
- Whether position encoding, attention, retrieval, and cross-segment induction are usable in long contexts.
- Whether the underlying distribution of code, math, tool trajectories, and complex instructions has entered the model's parameters.
- Whether subsequent SFT/RL can more easily elicit these capabilities.

Post-train cares about:

- Instruction following, answer style, safety refusals, preference ranking.
- Multi-turn dialogue and alignment with user intent.
- Whether the reasoning process is made explicit and whether it fits product policy.
- Reward-optimizable behavior in RL/RLHF/RLAIF/RLVR.

Roughly speaking, mid-train leans toward changing capability reachability and the in-parameter distribution, while post-train leans toward changing the task interface, behavioral policy, and product presentation; but on reasoning, tool use, agent, and long-context tasks, the two overlap, and a paired protocol is needed to determine where the gains come from.

### 1.3 Not everything should be called mid-train

This piece does not simply classify the following as mid-train:

- Large-scale general pretraining from scratch.
- SFT purely for alignment, safety, or formatting.
- Continuing to run language modeling on post-train data alone, without a capability target, data control, or regression evaluation.
- RAG, external tools, inference-time search, and other systems engineering that does not change model parameters.

The boundary needs to be clear — otherwise the team will manage mid-train with post-train's evaluation methods and organizational approach, and it will end up very hard to tell where the gains came from.

### 1.4 Ten points of differentiated understanding for foundation model teams with post-train experience

1. Mid-train's object is the capability distribution, not the answer style.
2. Mid-train's primary loss usually still stays close to the language-modeling objective, not preference optimization.
3. Mid-train data can include QA/CoT/FIM, but the entire SFT dataset should not be moved forward wholesale.
4. A good mid-train checkpoint is not necessarily the checkpoint with the lowest loss — it's the Pareto point between capability gain and forgetting.
5. Mid-train's gains must be observed in both base eval and post-train readiness.
6. Data contamination is more dangerous in mid-train than in SFT, because it feeds into judgments about base capability.
7. Synthetic data must be validated and stratified first — its proportion should not be raised just because it's "cheap."
8. Long-context capability must distinguish training length, inference extrapolation length, and servable length in production.
9. RL's gains usually depend on a capability range the base already has reachable; not every reasoning problem can be handed off to RL.
10. There must be a stop condition before scaling up training; mid-train is not "keep running because the budget isn't spent yet."

## 2. Strength tiers of public evidence

Public materials are not entirely consistent, and the easiest mistake is conflating "the training stage a report explicitly states," "a researcher's generalization," and "industry experience from an interview." This piece uses materials in three strength tiers.

### 2.0 This piece's evidence labels

To avoid mixing public facts with engineering inference, the rest of this piece defaults to four evidence labels:

| Label | Meaning | Can be used for | Cannot be used for |
| --- | --- | --- | --- |
| Report fact | Stages, tokens, context, data types, or training objectives directly disclosed by a technical report, paper, or official material | Describing what a given team actually did | Concluding that other teams should copy the same recipe |
| Paper generalization | Mechanisms, taxonomy, or variable relationships from a survey or controlled experiment | Designing internal ablations, forming hypotheses | Upgrading directly into an industry-wide training law |
| Engineering generalization | Conservative practice recommendations this piece distills from multiple cases | Setting up project process, gates, ledgers, and risk control | Claiming to be the literal conclusion of some specific report |
| Unverified hypothesis | Directions inspired by interviews, blog posts, industry lore, or small-sample experiments | Entering the small-model/short-run experiment backlog | Entering a main-model scale-up decision |

Readers should treat "report facts" as the factual bedrock, treat "paper generalizations" and "engineering generalizations" as inputs to experiment design, and treat "unverified hypotheses" as a backlog. Any decision that will consume large-scale training budget should go back to the team's own data manifest, eval registry, and post-train paired protocol.

### 2.1 Strong evidence: stage designs explicitly disclosed in technical reports

Strong evidence refers to training stages, token scale, context length, or data strategy disclosed directly by a model team in a technical report.

| Case | Original report terminology | What the public report directly supports | This piece's engineering analogy |
| --- | --- | --- | --- |
| OLMo 2 | mid-training | A clear layering of pretraining -> mid-training -> instruction/preference tuning; relatively transparent details such as the Dolmino Mix, 50B/100B/300B, and micro-annealing | Public reference sample for narrow-sense mid-training |
| Qwen3 | pre-training stages | Three pre-training stages — General / Reasoning / Long Context; roughly 36T total tokens, roughly 5T reasoning-stage tokens, 32K long-context training | mid-train-like capability shaping + context adaptation |
| DeepSeek-V3 | long context extension | After 14.8T-token base pre-training, two rounds of 1000-step context extension using YaRN, from 4K -> 32K -> 128K | mid-train-like long-context extension, but mainly supports a staged-length-extension conclusion |
| Qwen2.5-1M | long-context pre-training / post-training / inference scaling | Progressive long-context pre-training, long-context post-training, DCA/YaRN extrapolation, and sparse-attention/chunked-prefill deployment optimization | A joint sample of context adaptation + inference/deployment |
| Phi-4 | pretraining / midtraining / post-training | Synthetic data runs through pretraining/midtraining/post-training; midtraining explicitly extends context from 4K to 16K | A boundary sample of synthetic-heavy training strategy + context extension |
| Llama 3 | initial pre-training / long-context pre-training / annealing | 405B underwent initial pre-training on 15.6T tokens, roughly 800B tokens of long-context pre-training up to 128K, followed by a 40M-token annealing phase | A conservative reference for late-stage continued pre-training and annealing |

These reports can support "the existence of staged design," but usually cannot support "copying the data ratios or learning rate." Undisclosed tokenizer, data cleaning, sampling strategy, base checkpoint state, optimizer state, and system implementation all significantly affect the outcome.

### 2.2 Medium evidence: generalizations from surveys and controlled experiments

Research such as mid-training surveys, PRISM, and studies on pre-training/mid-training/RL interplay can help a team understand variable relationships: data retention versus capability transfer, whether a capability sits at the model's reachable edge, and whether RL can benefit from a mid-trained checkpoint.

The value of this research is proposing mechanistic hypotheses and experimental dimensions, not handing over a directly-extrapolable industry recipe. Conclusions from controlled synthetic tasks or small-scale models in particular should not be upgraded directly into "training laws for all large models."

### 2.3 Weak evidence: interviews, blogs, and industry lore

Interviews and blogs usually provide two kinds of information: how practitioners use terminology, and how a team describes the organizational logic of its training stages. But this kind of material often omits failed experiments, data details, and engineering constraints, so it can only serve as background on trends — not as hard fact.

If an interview claims some stage is "very important," this piece treats it as an unverified hypothesis; it only enters a training decision once it is backed by a technical report, a reproducible experiment, or the team's own internal ablation.

### 2.4 A conservative consensus drawn from public material

First, mid-train-like stages generally occur after base capability has formed and before post-training. OLMo 2 is the narrow-sense sample; Qwen3, DeepSeek-V3, Qwen2.5-1M, and Llama 3 are engineering-adjacent samples that use different terminology.

Second, in cases such as OLMo 2, Qwen3, Phi-4, and Llama 3, late-stage / continued pre-training tends to come with stronger data filtering, capability-oriented sampling, or an increased share of high-quality data; but a context-extension case like DeepSeek-V3 mainly supports staged length extension, and does not directly support a data-ratio conclusion. A safer statement is: the marginal value of late-stage tokens depends more on quality, mix ratio, and training objective than on simply appending more web tokens.

Third, long context is not just about changing RoPE scaling. Real long-context capability requires training data, a length curriculum, position/attention mechanisms, an inference framework, and evaluation tasks to all hold together. DCA, YaRN, sparse attention, and chunked prefill each act at different points — some affect training feasibility, others mainly serve inference extrapolation and deployment cost.

Fourth, reasoning mid-train is better treated as a strong engineering hypothesis for "improving the substrate available to RL," rather than an already-proven universal law. A more conservative statement: if a base/mid-trained checkpoint has zero solvability on the target task, RL usually struggles to reliably produce the capability; but whether RL delivers a genuine capability gain still depends on pretraining exposure, whether the task sits at the model's capability edge, reward design, and exploration budget.

Fifth, synthetic data has value, but it isn't a free lunch. Phi-4 shows that synthetic data can significantly affect reasoning performance, while also reminding teams that organic data is still needed to fill in world knowledge, expressive diversity, and real-world distribution.

Sixth, a transparent experiment ledger matters more than a single leaderboard number. One of the biggest values of a report like OLMo 2's is that it separately describes pretraining, mid-training, post-training, and data composition, helping later teams build their own lineage, bucketed loss, and regression evaluation.

Seventh, public reports can prove "some mature teams adopted staged late-stage training," but they rarely prove "some specific data ratio, learning rate, or token budget is universally optimal." All the recipe tables later in this piece should be read as a search space and a set of quality gates, not as a recipe copied from some model's report.

This chapter is not a rehash of model reports, nor a recipe source. It answers only one question: what evidence can public cases provide for a new team's mid-train project, and what cannot be extrapolated. Read the case-evidence summary table first; only read the case-by-case notes when you need to check factual boundaries.

The cases in this chapter answer only "what public material can prove and what internal experimental variables it can inspire" — they do not provide a reproducible training recipe. ### 3.1 OLMo 2: the clearest public mid-training paradigm

OLMo 2 explicitly calls its second stage mid-training: the first stage is large-scale pretraining, the second stage trains on a high-quality data mix such as the Dolmino Mix, and after that comes instruction tuning and preference tuning. The report also discloses mid-training token samples such as 50B/100B/300B, along with details like micro-annealing and checkpoint averaging. It is best used as a transparent public reference sample, not as the default organizational template for every team.

Internal hypotheses/check items it can be turned into:

- Make mid-train an independent stage with clear inputs, outputs, and an eval gate.
- Don't mix all data together — clearly distinguish sources such as Dolma, DCLM, StarCoder, and OpenWebMath.
- Retain an independent evaluation of the base checkpoint before post-train.
- Use small-scale late-stage experiments like micro-annealing to help decide whether a recipe is worth scaling up.

Parts that should not be extrapolated:

- OLMo 2's public recipe is not the optimal recipe for every team. Its value is transparency and learnability, not direct replication.
- Its data structure leans toward the open-source English ecosystem; goals such as Chinese, multilingual, tool use, or agentic coding require rebuilding the data buckets.

### 3.2 Qwen3: General -> Reasoning -> Long Context

The Qwen3 technical report calls the relevant stages "Pre-training Stage," not mid-training. The disclosed three-stage path is:

- General Stage: roughly 36T total pretraining tokens, of which S1 exceeds 30T tokens, covering general language knowledge.
- Reasoning Stage: roughly 5T tokens of high-quality STEM, code, reasoning, and synthetic data, strengthening task-relevant capability.
- Long Context Stage: several hundred billion long-context tokens, extending the training length to 32K.

This shows that a mature team will design late-stage training around multiple capability targets rather than a single, undifferentiated "continued training" stage.

Internal hypotheses/check items it can be turned into:

- Design capability-oriented mid-train and long-context mid-train separately.
- The second stage looks more like capability shaping, the third stage more like context adaptation.
- Distinguish training length from inference-supported length: Qwen3's reported training stage extends to 32K; ABF is a RoPE base-frequency adjustment, while YaRN and DCA are used to further support longer inference lengths.
- Evaluation should also be split: STEM/code/reasoning should look at specialized benchmarks and real tasks; long context should look at long documents, long code, and multi-evidence tasks.

Parts that should not be extrapolated:

- Qwen3's full data mix is not fully disclosed, so its macro-level stage design should not be treated as a copyable recipe.
- Whether to prioritize capability enhancement or long context depends on the product goal. If the product goal isn't long-context-first, and the existing context already satisfies the main tasks, then prioritize capability shaping instead.

### 3.3 DeepSeek-V3: context extension and engineering constraints after a large-scale base

The DeepSeek-V3 report offers two signals important for mid-train:

- 14.8T high-quality, diverse tokens correspond to the base pre-training stage.
- After base pre-training, YaRN is used for two stages of long-context extension, each 1000 steps, first from 4K to 32K, then from 32K to 128K.

In addition, DeepSeek-V3's training also includes architecture and training designs such as MLA, DeepSeekMoE, auxiliary-loss-free load balancing, and MTP. For a mid-train team, this is a reminder: if the base architecture, position encoding, MoE routing, attention memory, and inference framework don't support it, better late-stage data still may not reach the target.

Internal hypotheses/check items it can be turned into:

- Long-context extension should be staged, not pushed to the target length in one step.
- Before context extension, confirm that the inference framework and attention kernel can carry the deployed form after training.
- When training toward multiple targets, monitor MoE load balance, training stability, and per-bucket loss.

Parts that should not be extrapolated:

- DeepSeek-V3 is a large system deeply co-designed from architecture through training — the long-context stage cannot be isolated and copied.
- Many of the key efficiencies in its report come from systems and architecture; the data/training stage is only part of the whole.
- The 128K capability demonstration includes tests like NIAH, which alone cannot prove the full capability for real long documents, long code, and online serving.

### 3.4 Phi-4: a synthetic-heavy training strategy, not a clean reasoning mid-train

Phi-4 is better used as a case of synthetic-heavy training strategy, not a clean "reasoning mid-train" recipe. The report does emphasize synthetic data for pretraining and midtraining; at the same time, its explicit midtraining stage mainly handles long-context expansion, extending context from 4K to 16K over roughly 250B tokens. This piece's characterization of reasoning gains is an engineering generalization: the public report can support the idea that synthetic data, curriculum design, data mixing, and post-training all matter, but it cannot precisely attribute the contribution of each part.

Internal hypotheses/check items it can be turned into:

- Math, code, logical reasoning, and textbook-style explanations are all well suited to introducing verifiable or semi-verifiable synthetic data.
- Synthetic data is best paired with a pipeline for generation, filtering, verification, deduplication, difficulty stratification, and stylistic diversification.
- On small models, first look at how synthetic-data proportion, question difficulty, answer length, and correctness filtering affect final capability.

Parts that should not be extrapolated:

- Synthetic data will amplify the teacher model's biases and errors.
- If the generation templates are too uniform, the model will learn to "look like it's reasoning" in a superficial format.
- Open-domain knowledge, real user queries, and multilingual expression still require high-quality organic data mixed in.

### 3.5 Qwen2.5-1M: training scale-up, inference extrapolation, and deployment optimization should be kept separate

The Qwen2.5-1M report shows how long-context capability is jointly constructed from training, post-training, inference extrapolation, and the deployment system. One misreading in particular needs to be avoided: 1M context is not simply trained directly through mid-train data, but that doesn't mean training doesn't matter.

A more precise breakdown is:

- Long-context pre-training: uses progressive pre-training, advancing roughly along a 4K -> 32K -> 64K -> 128K -> 256K length path, using natural long documents, synthetic long-context tasks, and a length-distribution curriculum.
- Post-training: uses long instruction data and multi-stage post-training to make the model better at completing user tasks within long contexts.
- Inference / deployment: 1M support comes from the combination of 256K long-context training and DCA/YaRN extrapolation; sparse attention, chunked prefill, and vLLM/BladeLLM adaptation mainly serve deployment cost rather than an ordinary mid-train data recipe.

Internal hypotheses/check items it can be turned into:

- Long context is a capability jointly defined by model, data, training, and inference framework.
- Going straight from 4K to 1M is extremely high-risk; it's better to validate training/inference consistency step by step at 8K/16K/32K/128K/256K.
- Evaluation should avoid a single needle metric, and should include complex long-document QA, long code, tables, cross-segment reasoning, and robustness tests.

Points to note:

- The cost and deployment complexity of 1M context is very high and may not suit every product.
- For most teams, high-quality usability at 32K/128K may have more commercial value than demonstrating 1M capability.

### 3.6 Llama 3: a conservative sample of initial pre-training + long-context + annealing

The Llama 3 series reports do not call the relevant stages mid-training, but they offer a valuable conservative sample. Taking the 405B model as an example, the report discloses that initial pre-training used an 8K context over roughly 15.6T tokens; subsequent long-context pre-training used roughly 800B tokens, extending in six stages from 8K to 128K; finally, 40M tokens of learning-rate annealing brought the rate down to zero, while keeping the 128K context and upweighting some high-quality data.

Internal hypotheses/check items it can be turned into:

- Late-stage training can handle both long-context adaptation and quality convergence at once, but must keep running general-capability regression throughout.
- Annealing is not a slogan for "training a bit more" — it's a stage tied to data quality, learning rate, and checkpoint selection.
- If a team wants to stay conservative, Llama 3's lesson is not to chase complicated tricks, but to break continued training, long context, and end-stage convergence into observable steps.

Parts that should not be extrapolated:

- The specific token counts and data recipe in the Llama 3 report depend on its large-scale foundational training, and should not be transplanted as a small team's default budget.
- Its long-context and subsequent instruction-model capability are also affected by post-training and system implementation.

### 3.7 PRISM and pre/mid/RL research: treat mechanistic hypotheses as hypotheses

The value of papers like PRISM and studies on the interplay of pre-training, mid-training, and RL is that they turn several long-debated, experience-based questions into experimentable ones: how mid-training affects retention, which capabilities reinforce or interfere with each other during continued training, and whether RL depends on capability boundaries already exposed during the pre/mid stages.

Internal hypotheses/check items it can be turned into:

- Split "retaining old capability" and "injecting new capability" into two separate metrics, rather than looking only at target-capability growth.
- Use whether a task sits at the model's edge-of-competence as a pre-check before RL.
- Treat controlled-experiment conclusions as inputs to ablation design, not as direct conclusions for main training.

Points to note:

- This kind of paper is usually controlled in scale, task, and data distribution, and must be re-validated whenever extrapolated to an industrial model.
- Judgments about reasoning in particular need to stay conservative: RL may amplify existing capability, but it may equally amplify reward loopholes and formatting bias.

## 4. A design framework for mid-train

Read this chapter first through the lens of the first-round minimal closed loop: Gate 0 freezes the target capability, non-negotiable capabilities, eval registry, and post-train paired protocol; Gate 1 freezes the data manifest; Gate 2 uses a control mix plus 3-5 single-variable variants at proxy scale to rule out bad directions; Gate 3 uses short-run training on the target model to find the capability/forgetting Pareto checkpoint; Gate 4 uses the same frozen post-train paired protocol to validate whether the gains are retained. Sections 4.1-4.6 explain, respectively, the goals, data, training knobs, ablation, curriculum, and organizational quality gates within this closed loop.

An executable mid-train project should ultimately answer five questions: what the target capability is, which capabilities must not regress, which data buckets drive the capability, how training length/learning rate/context curriculum should be set, and how to prove it helps post-train.

### 4.0 The first-round minimal closed loop

The first time you do mid-train, don't design a complete training system up front. The "minimal closed loop" here is not a minimal training recipe — it is a minimal evidence chain: validate, at the smallest possible experimental cost, whether data, training, evaluation, and the post-train handoff can together produce an interpretable conclusion. First get one goal, one primary hypothesis, one set of data buckets, one eval registry, one short-run training window, and one frozen post-train paired protocol working end to end.

| Loop stage | Answers only one question | Minimal evidence | Where to go back to on failure |
| --- | --- | --- | --- |
| Goal | Why must this be mid-train | Target capability, non-negotiable capabilities, ruling out alternatives | Back to the charter — change the goal, or don't do mid-train |
| Data | Which bucket might drive the target capability | Data manifest, contamination check, linked eval, manual samples | Back to the data-bucket admission card |
| Training | Does a low-risk short run show directional gains | Checkpoint curves and per-bucket loss at fixed LR/mix/context | Back to training knobs or data mix |
| Evaluation | Is the gain not a public-leaderboard or formatting false positive | Private holdout, raw output, manual review, scorecard | Back to the eval registry |
| Handoff | Do gains survive post-train | Paired SFT/RL protocol, seed, AUC, failure samples | Back to the post-train recipe or the mid-train goal |
| Decision | extend / rollback / kill | Gate dashboard, evidence_path, owner sign-off | Back to the corresponding gate |

Chapter 11 provides a sample search grid for this loop — not a default recipe. Chapter 4 covers the design objects, Chapters 6-8 cover how to judge evidence, and Chapter 11 provides an executable starting-point sample.

### 4.1 Layering the capability target

It is recommended to split the target into four layers:

Layer 1: general base fidelity

- General language-modeling loss does not rise abnormally.
- Common sense, factual knowledge, multilinguality, and basic instruction comprehension do not regress noticeably.
- Multi-turn dialogue, while not mid-train's main target, must at least stay basically coherent.

Layer 2: core capability enhancement

- Math: GSM8K, MATH, AIME-style benchmarks, plus internal verifiable question banks.
- Code: HumanEval, MBPP, EvalPlus, repo-level completion, FIM, multi-file localization, etc.; SWE-bench is better suited for use with a fixed harness, light instruction wrapping, or the post-train readiness stage.
- STEM: GPQA, MMLU-Pro, domain question banks.
- Reasoning: BBH, ARC, logical reasoning, complex QA.

Layer 3: structural capability

- Long-context retrieval, synthesis, and conflict resolution.
- FIM, code completion, multi-file editing.
- Table, log, long-PDF, and long-meeting-transcript comprehension.

Layer 4: post-train readiness

- Whether the model learns the target format more easily after SFT.
- Whether it improves more stably after RL/RLVR.
- Whether reward hacking decreases.
- Whether the reasoning trace becomes more controllable.

### 4.2 Data-bucket design

At minimum, it's recommended to establish the following data buckets:

| Data bucket | Goal | Main risk | Recommended control |
| --- | --- | --- | --- |
| High-quality web / books | Preserve general language and world knowledge | Noise, duplication, copyright/compliance | Deduplication, quality classification, sampling caps |
| Code | Programming ability, formal structure | License, duplication, benchmark leakage | License filtering, repo-level dedup, question-bank isolation |
| Math / STEM | Reasoning and symbolic ability | Overfitting to competition problems, wrong answers | Verifiable problems, difficulty stratification, proof/answer checking |
| Synthetic textbook | Concept compression, teaching-style reasoning | Uniform style, teacher errors | Multiple teachers, multiple templates, verifier filtering |
| QA / CoT | Reasoning traces and task format | Prematurely locking in post-train behavior | Control the proportion, retain natural text |
| Long documents | Long-context adaptation | Empty padding, inefficient tokens | Real long documents + synthetic long tasks |
| FIM / code editing | Coding-agent capability | Distorting the ordinary LM distribution | Bucketed loss and code eval |
| Domain data | Industry/product capability | Catastrophic forgetting, over-narrowing | Low-proportion mixing, general regression |

Don't build just one global mix. Each bucket needs:

- A record of data source and license.
- A deduplication strategy.
- A quality score.
- A contamination check.
- A sampling ratio.
- Its own loss.
- A corresponding eval.

### 4.2.1 Data-bucket admission card

Every data bucket should enter the data manifest before it goes into training — never straight into the mix. The minimal fields are:

| Field | Description |
| --- | --- |
| `bucket_id` / `bucket_name` | Data bucket number and name |
| `source_manifest` | Original source, time range, license / compliance status |
| `processing_commit` | Version of cleaning, parsing, and filtering scripts |
| `dedup_version` | Deduplication version at document, paragraph, code-repo, or problem level |
| `contamination_version` | Contamination-check version against public benchmarks, private holdout, and synthetic prompts |
| `tokenizer_version` | Tokenizer and special-tokens version |
| `quality_score_distribution` | The distribution of quality scores, not just the average |
| `language_domain_distribution` | Distribution of language, domain, file type, and length |
| `time_distribution` | Data time range, old/new distribution, whether it includes events newer than training cutoff |
| `sampling_weight` | Current sampling weight and cap in the mix |
| `shuffle_seed` / `bucket_interleaving` | Data ordering, bucket-interleaving strategy, whether the mix changes across stages |
| `bucket_validation_loss` | Per-bucket validation loss and abnormal changes |
| `linked_eval_id` | The corresponding evaluation item in the eval registry |
| `known_risks` | License, contamination, templating, duplication, factual errors, overly narrow distribution |

The data-bucket admission gate should be written as hard rules:

- No manifest/hash, no entry into training.
- No corresponding eval, no increase in sampling weight.
- Unresolved contamination hits, no entry into a primary experiment.
- Synthetic data without correctness filtering and style-diversity checks may not exceed a low exploratory proportion.
- Domain data without general-regression protection may not enter the main-model short run.
- Long-context data that is only concatenated text with no real long tasks may not enter the primary long-context mix.
- Any action that changes filters, quality models, dedup thresholds, sampling weights, synthetic generation prompts, or data order must generate a new `data_manifest_hash` and `experiment_id`.

### 4.2.2 Boundaries for using synthetic data

Synthetic data needs to be governed separately, because it is the most prone to "looking effective" on short-term metrics:

| Risk | Symptom | Control method |
| --- | --- | --- |
| Amplified teacher errors | Math/code answers look fluent but aren't verifiable | Executable verification, answer checking, sampled manual review |
| Stylistic templating | All output looks like the same teacher, fixed reasoning steps | Multiple teachers, multiple prompts, multiple solution paths, mix in organic data |
| Near-contamination of benchmarks | Large numbers of variants of public problems appear | Check problem stems, solution structure, embeddings, and translated duplicates |
| Distorted difficulty distribution | Training problems are too easy or cover only one problem type | Difficulty buckets, feed failure samples back in, compare against private holdout |
| Excessive CoT-behavior transfer | The base model prematurely learns a verbose explanation format | Control CoT proportion, mix in short answers, no-CoT, and natural text |

The sound use of synthetic data is as a "verifiable capability amplifier," not a low-cost token substitute. Math, code, and structured reasoning are well suited to heavy use of verifiable synthetic data; open-domain knowledge, language style, and multilingual expression still need a high-quality organic-data backstop.

Different types of synthetic data have different boundaries too:

| Synthetic data type | Good use | Bad use | Must-check items |
| --- | --- | --- | --- |
| Verifiable math/code | Improving symbolic reasoning, executable problem-solving, unit-test capability | Substituting for open-domain knowledge | Verifier, answer execution, difficulty buckets |
| Textbook-style explanation | Compressing concepts, filling in knowledge structure | Substituting for natural corpus at large proportion | Teacher diversity, expression templates, factual spot checks |
| CoT / rationale | Providing a reasoning-trace format | Prematurely locking the base model into a verbose answer style | CoT proportion, short-answer mixing, style drift |
| Synthetic long-context tasks | Covering scarce long-task patterns | Substituting for real long documents and long code | Evidence position, distracting information, unanswerable samples |
| Domain synthetic QA | Filling in domain task shapes | Substituting for real domain documents | Expert spot checks, source tracing, terminology consistency |

The synthetic bucket must also record the teacher model/version, generation prompt, sampling parameters, verifier version, filtering rules, rejected-sample rate, template repetition rate, answer verifiability rate, human-review error rate, and whether the generator has seen the eval/benchmark. Synthetic CoT/QA additionally needs checks on style entropy, template n-grams, and response-length distribution, to avoid prematurely locking in post-train behavioral formats.

### 4.3 Learning rate and token budget

Public reports usually don't disclose every detail, but there are several robust engineering principles.

First, mid-train usually should not use a learning rate close to early-pretrain levels. The model has already formed a large amount of general capability, and too high a learning rate causes forgetting, style drift, and loss spikes.

Second, the LR strategy should match the goal:

- Short-run capability enhancement: continue training at a low learning rate, watching target capability and general regression.
- Late-stage annealing: lower the learning rate further, converging on high-quality data.
- Context extension: keep the LR more conservative, paired with a length curriculum.
- Domain adaptation: token budget and data ratio need even tighter limits, to avoid narrowing the model.

Third, token budget is not "the bigger the better." The three tiers below are only conservative starting-point scales for launching experiments — they don't scale linearly across model sizes, and they can't replace a scaling ablation:

- 1B-10B tokens: for pipeline, data quality, LR, contamination checks, and proxy ablation.
- 10B-100B tokens: an example range for observable capability enhancement and small/medium-model recipe validation; the actual budget should be decided by model scale, data quality, and gate results.
- 100B-1T+ tokens: only suitable once relatively complete capability shaping or long-context extension on the main model is warranted.

The above are not industry laws, just conservative starting points. The real token budget should be jointly decided by model scale, data quality, target capability, and budget.

### 4.3.1 Recipe knobs and the "don't change everything at once" principle

Training variables need version-freezing just like data and eval. Every run should record at least:

| Variable | Why it needs freezing | Common misjudgment |
| --- | --- | --- |
| `base_checkpoint_hash` | Determines the starting capability and prior data exposure | Misattributing differences between base checkpoints as a mid-train gain |
| `optimizer_state_strategy` | Whether to continue or reset changes the loss curve and stability | Insufficient warmup after a reset produces false-looking regression |
| `lr_schedule` / `warmup` | Affects forgetting, convergence, and loss spikes | Comparing only final scores, not training stability |
| `peak_lr` / `min_lr` / `decay_shape` | Determines the actual optimization trajectory | Everything labeled "low LR" while the training dynamics differ completely |
| `gradient_clipping` / `precision` | Affects stability and numerical error | Misattributing numerical instability to a data-mix problem |
| `global_batch` / `microbatch` | Changes effective batch size and training noise | Small-batch noise misjudged as capability fluctuation |
| `sequence_length_distribution` / `length_bucket_ratio` | Changes the effective token distribution and training dynamics | Attributing length-change gains to the data mix instead |
| `data_order` / `shuffle_seed` | Curriculum, annealing, and long-context stages are order-sensitive | The same mix in a different order yields opposite conclusions |
| `packing_policy` / `masking_policy` | Affects FIM, long-document, and short-sample proportions | Global loss looks fine while short tasks regress |
| `checkpoint_selection_policy` | Determines what's actually being compared | Cherry-picking the best checkpoint after the fact inflates the gain |
| `eval_cadence` | Determines when forgetting and drift are discovered | Not discovering irreversible regression until training has ended |

Scale-up should also stay conservative. Proxy success only shows a direction is worth pursuing further — it doesn't guarantee the target scale will succeed. Before moving to larger training, at least four conditions should be met:

1. Two scale runs, or the target's short run, point in the same direction.
2. Changes in per-bucket loss, target eval, and base regression can be explained by the same data/training hypothesis.
3. Under the same mix, different seeds don't reverse the conclusion, and training throughput, checkpoint resume, and monitoring have all been verified.
4. It's cost-acceptable: if scaling tokens up 10x would only buy a marginal, small gain, improve the data or eval first rather than adding budget.

Don't change too many knobs in one experiment. It helps to look at common knobs separately:

| Knob | How to adjust | Main risk | Signal to watch | When to stop |
| --- | --- | --- | --- | --- |
| LR / warmup | Low LR, further lowering, short warmup sweep | Forgetting, loss spikes, slow convergence | Global loss, per-bucket loss, gradient norm | Spike doesn't recover, or fidelity metrics drop fast |
| Token budget | Incrementally increase short-run budget | Wasted budget, overfitting a narrow distribution | Delta between checkpoints, Pareto curve | Marginal gain disappears or regression widens |
| Sequence length | Gradually extend the length distribution | Long training hurts short tasks, throughput drops | Per-length-bucket loss, short-task regression | Short tasks regress significantly or serving cost becomes unacceptable |
| Batch / packing | Change packing, mix long and short samples | Effective data distribution changes | Throughput, padding, short-sample loss | Global loss looks fine but bucket loss is abnormal |
| Optimizer state | Continue or reset | Inherited momentum, or insufficient warmup | Early loss, gradients, resume continuity | Early instability that can't be explained |
| Synthetic ratio | Gradually raise the cap | Templating, amplified teacher errors | Private eval, style review, failure samples | Style collapse, or private set stops improving |
| Domain ratio | Low-proportion mixing | Model narrows, general capability regresses | General regression, private domain tasks | Domain gain is smaller than the cost of general regression |

### 4.4 First-round ablation design table

The first round should not chase "the best recipe" — it should quickly rule out wrong directions. The ratios in the table below are only example search variables, used to expose sensitivity and bad directions — they should not be used as a default main-training mix.

| Experiment purpose | Example model scale | Example token budget | Example data-mix search variables | LR variable | Success metric | Stop condition |
| --- | --- | --- | --- | --- | --- | --- |
| Pipeline and eval calibration | Proxy model, e.g. 1B/3B | 1B-3B tokens | Small-sample full-bucket mix | Single low-LR point | Normal loss, reproducible eval | Loss spike, unstable eval |
| General-fidelity floor | Proxy model, e.g. 3B/7B | 3B-10B tokens | General high-quality share 30/50/70% | Fixed low LR | General-capability regression stays controlled | Multilingual/factual scores collapse |
| Math/STEM injection | Proxy model, e.g. 3B/7B | 5B-20B tokens | Math/STEM share 10/20/30% | Low LR + even lower LR | Math improves without general collapse | Only public problem types improve |
| Code/FIM injection | Proxy model, e.g. 3B/7B | 5B-20B tokens | Code/FIM share 10/20/30% | Fixed low LR | Completion/FIM/repo-task gains | Ordinary generation becomes noticeably code-like |
| Synthetic-data proportion | Proxy model, e.g. 3B/7B | 5B-20B tokens | Synthetic share 5/15/30% | Fixed low LR | Verifiable tasks improve, style stays diverse | Templating or contamination risk |
| Main-model short-run validation | Target model | 10B-100B tokens | 2-3 candidate mixes | Low-LR sweep | A Pareto checkpoint emerges | Target capability doesn't improve or forgetting is too large |

The output of these experiments is not a final model — it's a decision: which data bucket works, which ratio is risky, which LR range is safe, and whether it's worth moving to a longer main run.

### 4.4.1 How to read an ablation

The output of an ablation is ruling out bad directions and forming Pareto candidates, not proving a final recipe. Five rules for reading them:

1. Proxy success does not equal target success; before moving to the main model you need two scales pointing the same direction, or confirmation from a target short run.
2. A rise on a single public leaderboard does not equal a capability gain; it must be viewed together with private holdout, failure-sample clusters, and manual review.
3. A target-capability gain must be viewed alongside guardrails; if math/code go up while multilinguality, factuality, and natural generation clearly go down, that is not a clean gain.
4. Results near a threshold should be re-run or checked against neighboring checkpoints; don't make a scale-up decision on a single seed's small gain.
5. Any experiment where the mix, filter, LR, length curriculum, or eval version was changed mid-run must reopen with a new experiment_id.

### 4.5 Curriculum: capability first, then length, or in parallel?

New teams should not start by mixing all goals together.

A more stable order is:

1. Base-fidelity check: confirm the checkpoint, tokenizer, optimizer state, data pipeline, and evaluation system are all usable.
2. Capability-oriented mid-train: math/code/STEM/high-quality synthetic data, short-run ablation.
3. Long-context adaptation: extend gradually from a shorter context, monitoring long-context loss and real tasks separately.
4. Small-scale post-train handoff: use a fixed SFT/RL recipe to compare checkpoints before and after mid-train.
5. Decide whether to merge into the main training recipe.

Why capability before length? Because long-context training is expensive, hard to debug, and easily conflates architecture problems with data problems. If the model's underlying reasoning/coding ability hasn't improved, a longer context only enlarges the input window — it doesn't necessarily enlarge task capability.

There are exceptions too: if the product goal really is legal/financial long-document QA or a codebase agent, long context can be moved earlier, but it should still be validated on small models first.

| Product's primary goal | Recommended priority | First-round validation | Contrary signal |
| --- | --- | --- | --- |
| Math, code, STEM, complex QA | Capability first, then length | Short-run ablation on capability bucket + general-fidelity bucket | Target capability improves only on public benchmarks, not on private tasks or manual samples |
| Legal/financial/scientific long-document QA | Capability and length in parallel, but as two separate experiment IDs | One capability short run, one 32K/64K context short run | Long-context retrieval is fine but synthesis/conflict/unanswerable tasks are poor |
| Codebase agent / repo-level editing | Code/FIM and mid-length context in parallel | FIM/repo tasks, long-code localization, short-code regression | Repo tasks improve but ordinary code generation or short tasks regress notably |
| Domain continued training | Low-proportion domain first, then decide on length | Domain bucket at 5/10/20% + general regression | Domain-task gain is smaller than the cost of general-capability regression |
| Demonstrating long-context capability | Confirm product value first, then do context extension | Real long tasks, serving cost, short-task regression | NIAH looks good but real tasks, online cost, or short tasks don't hold up |

The long-context curriculum should record the length distribution, not just the max length. Each stage should at least record:

- The proportion of samples at 4K/16K/32K/64K/128K.
- The packing strategy, padding waste, and whether short samples are being oversampled.
- Sources of long samples: natural long documents, long code, synthetic long tasks, cross-document collections.
- Task structure: evidence density, unanswerable samples, conflicting evidence, multi-hop evidence, evidence position, output length.
- Whether the training kernel and the inference kernel are consistent.

Otherwise "extended to 128K" is just a max-length claim — it doesn't explain whether the model actually learned long-context understanding, long-range retrieval, or just learned to keep the loss from blowing up on longer inputs.

### 4.6 Organizational mechanics: roles, ledgers, and quality gates

A mid-train project is not a model continuation completed by the training team alone — it's a capability-shaping project in which data, training, eval, and post-train all share the same experiment ledger and the same set of quality gates. Every organizational concept must be tied to an engineering object: a checkpoint, a data manifest, an eval version, a gate, an owner, and a decision.

First, set a DRI — not a vague "multiple teams participate."

| Workstream | Sole DRI | Participating teams | Final call | Key deliverable |
| --- | --- | --- | --- | --- |
| Goal definition | Model Lead | Product/Domain, Eval, Post-train | Model Lead | Mid-train charter, non-negotiable capabilities, experimental hypotheses |
| Data construction | Data DRI | Research, Safety/Compliance, Eval | Data DRI + Safety/Compliance | Data-bucket description, data manifest/hash, lineage, contamination report |
| Training execution | Training Infra DRI | Model, Data, Infra | Training Infra DRI | Training runbook, LR/token-budget config, checkpoint ledger, incident log |
| Evaluation system | Eval DRI | Model, Product/Domain, Post-train | Eval DRI | Eval registry, private holdout, scorecard, manually reviewed samples |
| Post-train handoff | Post-train DRI | Eval, Safety, Model | Post-train DRI | Frozen post-train paired protocol, readiness report, alignment regression |
| Long-context systems | Infra DRI | Training, Eval, Serving | Infra DRI + Eval DRI | Kernel/serving consistency report, KV cache/latency/cost evaluation |
| Risk and release | Safety/Compliance DRI | Data, Product, Release | Decision owner | Compliance review, risk register, go/no-go memo |

Second, the experiment ledger needs a fixed schema. Experiments without a ledger entry cannot be used as the basis for a conclusion; any mid-run change to the mix, the filter, or the eval version must open a new experiment_id.

| Field | Description |
| --- | --- |
| `experiment_id` / `hypothesis` / `owner` | Experiment number, the hypothesis being tested, the single responsible owner |
| `base_checkpoint_hash` / `training_code_commit` | Starting checkpoint and training code version |
| `data_manifest_hash` / `data_bucket_ratio` | Data manifest, sampling weights, data-bucket ratios |
| `dedup_version` / `contamination_version` | Deduplication and contamination-check versions |
| `lr_schedule` / `warmup` / `optimizer_state_strategy` | Learning rate, warmup, whether the optimizer state was continued or reset |
| `token_budget` / `sequence_length_distribution` | Token budget and length distribution, not just the max length |
| `eval_suite_version` / `private_holdout_version` | Eval registry, private holdout, and harness commit |
| `seed` / `cost` / `incident_log` | Random seed, training cost, incidents, and remediation actions |
| `result_summary` / `decision` / `signoff` | Summary of results, the kill/retry/extend/promote decision, sign-off owner |
| `post_train_readiness_result` | Whether the gains hold after a fixed SFT/RL recipe |

Third, the sole authoritative dashboard for quality gates lives in section 8.0; this section only defines roles, ledger fields, and sign-off responsibilities. This piece cannot set thresholds for a team, but a gate memo should at minimum define: the minimum required gain in target capability, the maximum allowed regression in general capability, the private-eval pass rate, the maximum contamination-hit rate, loss-spike handling rules, style-drift criteria, and the retention ratio of gains after post-train. Any gate status, evidence path, version hash, or expiration follows the dashboard in section 8.0.

| Gate | Entry condition | Exit condition | Block condition | Sign-off |
| --- | --- | --- | --- | --- |
| Gate 0: charter | Target capability, non-negotiable capabilities, budget, and post-train handoff needs are clear | Mid-train charter approved; v1 eval registry and v1 post-train paired protocol status follow the section 8.0 dashboard | No DRI, no paired-protocol owner/schema, no private-holdout owner/schema | Model Lead, Eval DRI, Post-train DRI |
| Gate 1: data freeze | Data source, license, cleaning, dedup, and contamination checks complete | Data manifest/hash frozen, manual spot checks find no systemic errors | Benchmark leakage, unclear license, obvious synthetic-data templating | Data DRI, Safety/Compliance DRI, Eval DRI |
| Gate 2: proxy ablation | At least two candidate mixes and a fixed eval suite | Proxy is used only to rule out bad directions; before the main model, need two scales pointing the same way, or a target short run confirming key signals | Only public benchmarks improve, private tasks don't move, general capability collapses | Model Lead, Eval DRI, Data DRI |
| Gate 3: main-model short run | Training runbook, resume, monitoring, and kill switch are ready | A capability/forgetting Pareto checkpoint emerges, per-bucket loss is explainable | NaN, unrecoverable loss spike, abnormal gradients, abnormal throughput, discontinuous resume, long context hurting short tasks | Training Infra DRI, Eval DRI, Model Lead |
| Gate 4: post-train handoff | Paired-protocol recipe, seed, budget, harness, and failure criteria are frozen | Gains still hold under the fixed paired protocol after post-train, no significant safety/style deterioration | Mid-train gains disappear after post-train, the paired protocol changed mid-run, or alignment difficulty rises significantly | Post-train DRI, Eval DRI, Safety DRI |
| Gate 5: scale-up training | Source of the gain is explainable, data/eval/training automation is stable | Go/no-go memo approved, moving into the next budget stage | Gains depend on contamination, a narrow eval, a lucky checkpoint, or can't be reproduced | Decision owner, Model Lead, Release owner |

Fourth, the meeting cadence should serve decisions, not reporting:

- Daily training review: loss, throughput, NaN/loss spikes, checkpoints, resume, incident handling.
- Twice-weekly eval review: target capability, general regression, private holdout, manual sample review.
- Weekly decision review: kill, retry, extend, promote — decided only from the ledger and gate memos.
- Post-train handoff review: whether the paired protocol worked, whether gains held, whether safety and style regressed.

The bottom line of this mechanism: the calendar cannot substitute for the quality gates. The 90 days is only a reference cadence — whether to move to the next stage is decided by data readiness, training stability, eval stability, and post-train handoff validation.

## 5. Training-engineering checkpoints

### 5.1 Pre-launch checks

Before launching mid-train, you should complete:

- A full eval snapshot of the base checkpoint.
- The decision on whether to continue the optimizer state.
- Freezing the tokenizer and special tokens.
- Data deduplication and benchmark contamination checks.
- Sample review for every data bucket.
- A small-scale dry run confirming loss, throughput, memory, checkpointing, and resume all work.
- Post-train DRI confirmation of the paired protocol for the subsequent SFT/RL.

Without post-train handoff validation, mid-train can easily end up optimizing for the wrong target.

### 5.2 In-training monitoring

At minimum you need to monitor:

- Global training loss / validation loss.
- Validation loss broken down by data bucket.
- Regression on general-capability benchmarks.
- Gains on target-capability benchmarks.
- Loss across different long-context length segments.
- Style drift in generated samples.
- For MoE models: expert load, routing entropy, and token drop.
- Gradient norm, loss spikes, and inter-checkpoint differences.

Don't wait until training ends to run eval. Mid-train failures often show early signals: a sharp drop in general eval, templated output style, abnormal loss in some data bucket, or long-context training hurting short tasks.

### 5.3 Checkpoint strategy

It's recommended to keep:

- The pre-mid checkpoint.
- The early/mid/final checkpoint of each stage.
- Checkpoints from before and after learning-rate changes.
- A checkpoint at each stage of the context-length curriculum.
- Candidate checkpoints for the post-train handoff.

Don't keep only the last one. Mid-train's best checkpoint may not be the one with the lowest loss — it may be the Pareto-optimal point between target capability and forgetting.

### 5.4 Engineering risks that are easy to underestimate

First, mixed-length batching and context parallelism bring load imbalance. The throughput, memory fragmentation, padding waste, and communication pattern of long-context batches all differ from short-context ones — training monitoring must be split by length segment, or global throughput will mask local instability.

Second, both continuing and resetting the optimizer state can cause problems. Continuing the optimizer state is more like extending the original training trajectory, but it may inherit momentum from an earlier stage; resetting it is cleaner, but requires redesigning the warmup, or it easily produces loss spikes or overly slow convergence. Both approaches should first be tested at proxy scale.

Third, an inconsistency between the training attention kernel and the deployment attention kernel creates false positives. Passing offline eval does not mean the online 128K/1M service will work; long-context training, inference extrapolation, KV cache, chunked prefill, sparse attention, and the serving framework must be validated jointly.

## 6. The evaluation system

### 6.0 From a benchmark list to an eval registry

Mid-train's evaluation system is not a collection of leaderboards — it's a set of eval objects each with a version, contamination status, run harness, threshold, and archived raw output; a result that hasn't entered the registry can only be treated as an observation, not used as a go/no-go basis.

Each project should set at most 3-5 primary metrics, plus a number of guardrail and diagnostic metrics. Too many primary metrics invites cherry-picking; too few diagnostic metrics leaves the team unable to explain why something went up or down.

### 6.1 Minimal schema for the eval registry

The Eval DRI should freeze the v0 owner and schema at Gate 0, and freeze the v1 eval registry before Gate 1. The minimal fields are:

| Field | Meaning |
| --- | --- |
| `eval_id` | Unique identifier |
| `eval_family` | base regression / target capability / long-context / post-train readiness / safety-style |
| `task_name` | Task name |
| `data_source` | public / dev-private / sealed-private / final-blind / synthetic / human-written |
| `created_at` / `data_hash` | Creation time and data hash; private sets must predate the freeze of the corresponding training data mix |
| `split_policy` | dev / private holdout / regression set / final-blind |
| `contamination_check_version` | exact / n-gram / MinHash / embedding / paraphrase / translated duplicate / manual |
| `harness_commit` | Evaluation code version |
| `prompt_or_wrapper_version` | Version of the base prompt, minimal prompt, few-shot policy, light instruction wrapper, or agent harness |
| `decoding_params` | temperature, top_p, max tokens, pass@k, etc. |
| `metric` / `aggregation` | accuracy, pass@k, F1, judge score, latency/cost, etc., and the aggregation method |
| `decision_role` | primary / guardrail / diagnostic |
| `threshold_or_guardrail` | Improvement threshold, maximum allowed regression, failure condition, minimum meaningful difference |
| `sample_size` | Sample size and sampling rule |
| `manual_review_rubric` | Rubric for cases requiring manual review |
| `raw_output_path` | Location of archived raw output |
| `owner_note` | An explanatory note, not organizational responsibility |

The eval version-change rule must be written in stone: changing the samples, the prompt, the answer extractor, the metric, the harness, or the threshold all require generating a new `eval_suite_version` — old and new results must not be compared side by side.

Private holdout should be organized into three tiers:

- dev-private: for tuning the pipeline and calibrating the harness; not used for the final gate.
- sealed-private: used at stage gates; tuning the data mix or prompt against it is forbidden.
- final-blind: used only at Gate 5 or before release, to avoid it being repeatedly optimized against and turning into "another training target."

### 6.2 Eval suite matrix

| Eval family | Purpose | Representative task | Applicable checkpoint | Metric | Failure signal | Raw-output requirement |
| --- | --- | --- | --- | --- | --- | --- |
| Base regression | Protect non-negotiable capabilities | General knowledge, multilinguality, basic generation, factual QA | pre-mid, mid, post-train | Max regression, low-scoring-bucket change, manual review | Average score dips slightly but some language/style collapses | Complete output for a fixed sample basket |
| Target capability | Judge whether the target capability is truly stronger | Math, code, STEM, domain tasks, FIM | pre-mid, mid | Delta, difficulty-bucket breakdown, private-task pass rate | Only public leaderboards improve, private tasks don't move | Success/failure sample clusters |
| Long-context | Judge whether long context is usable | Multi-evidence QA, conflict resolution, long-code localization, long tables/logs | mid, post-train | Length-bucket performance, short-task regression, latency/cost | Perfect on needle but poor on real tasks | Input length, evidence position, backend config |
| Post-train readiness | Judge whether gains survive SFT/RL | Real tasks and safety evaluation after a fixed SFT/RL recipe | paired post-train checkpoints | Gain-retention ratio, training-curve AUC, variance | Improves on base but disappears after post-train | Recipe, seed, checkpoint-selection policy |
| Safety/style | Prevent drift in style, safety, and refusal | Safety set, refusal boundaries, writing quality, long-answer quality | mid, post-train | Regression rate, manual rubric, mistaken refusals | Templating, verbose CoT, more hallucination | Manually reviewed samples and rationale |

Target-capability eval answers "is the capability really stronger?"; base regression eval answers "did we hurt anything else?"; post-train readiness eval answers "does this base change still hold value after SFT/RL?"

### 6.3 Base regression eval

Base regression's focus is not proving the model is stronger — it's protecting non-negotiable capabilities. It should cover:

- General knowledge: MMLU, MMLU-Pro, internal knowledge questions.
- Reasoning: BBH, ARC, GPQA, logic questions.
- Math: GSM8K, MATH, AIME-style internal questions.
- Code: HumanEval, MBPP, EvalPlus, repo-level completion, FIM, multi-file localization.
- Multilinguality: Chinese, English, and target-market languages.
- Generation quality: long answers, summaries, explanations, translation, natural dialogue.

A base model may not reliably follow complex formats, so it's important to distinguish "insufficient capability" from "not following the format." Every base eval should record the minimal-prompting policy, few-shot policy, answer-extractor version, and manual-review rules. SWE-bench, agent tasks, and tool-use eval mix in instruction following, tool protocols, environment stability, and scaffold quality — they're better used as readiness/diagnostic metrics rather than raw base primary metrics.

The base-regression scorecard should report at minimum:

- The maximum regression on non-negotiable capabilities, not just the average score.
- Changes in low-scoring buckets and long-tail languages.
- Output style, refusal behavior, verbosity, and hallucination samples.
- Conclusions from a fixed manual-review sample basket.

### 6.4 Target capability eval

Target-capability eval must be kept separate from base regression. It doesn't just ask "did the public leaderboard go up" — it asks "is the target capability actually stronger on real and private tasks."

| Target capability | Evaluation method | Necessary safeguard |
| --- | --- | --- |
| Math/STEM | Difficulty buckets, verifiable answers, private problem variants, failure-sample clusters | Guard against near-duplicate competition problems and synthetic overfitting |
| Code/FIM | HumanEval/MBPP/EvalPlus, FIM, repo-level completion, multi-file localization | Use SWE-bench/tool-use as readiness or diagnostic |
| Domain capability | Private domain questions, real-document QA, expert manual rubric | Guard against domain data narrowing general capability |
| Agent/tool-use | Fixed harness, environment version, tool protocol, task trajectory | Don't mistake a better scaffold for a stronger base model |

If the target capability rises only on public benchmarks, and private holdout, failure-sample clusters, and manual review don't support it, first treat it as contamination, format adaptation, or narrow-distribution optimization.

### 6.5 Long-context eval

Long-context evaluation should be split into three layers:

- Mechanical retrieval: needle-in-a-haystack, multi-needle, at different positions and noise densities. This can only serve as a diagnostic — it should not enter the primary gate.
- Real comprehension: long-document QA, multi-chapter summarization, multi-evidence synthesis, conflicting-information judgment, long table/log analysis.
- Task completion: long-codebase edits, multi-file bug localization, legal/financial-report/paper synthesis, agent-trajectory review and next-step decisions.

The long-context eval registry must be laid out along axes:

| Axis | Required slices |
| --- | --- |
| Context-length bucket | 4K, 16K, 32K, 64K, 128K; add 256K/1M if the target is 1M |
| Task type | Retrieval, summarization, multi-evidence QA, code localization, cross-segment reasoning, unanswerable questions |
| Evidence density | Sparse facts, dense tables, long code, conflicting evidence |
| Distracting information | No distraction, same-topic distraction, contradicting evidence, stale information |
| Evidence position | Beginning, middle, end, multiple positions |
| Output requirement | Short answer, structured table, long answer, cited evidence |
| Inference backend | Attention kernel, KV cache, chunked prefill, batching, serving config |
| Cost constraint | Latency, throughput, memory, per-request cost |
| Short-task regression | Whether short tasks regress once placed inside a long context |

The hard gate for long context shouldn't just look at "can it run at the maximum length." A more reasonable bar is: short-context capability doesn't regress noticeably, mid-to-long-context real tasks show a gain, and the inference system's cost and latency at the target length are acceptable.

### 6.6 Post-train readiness eval

Post-train readiness should use a paired protocol:

- The pre-mid checkpoint and the mid checkpoint use the exact same frozen post-train paired protocol.
- Fix the data order, seed, budget, checkpoint-selection policy, reward/verifier, harness, decoding, and failure criteria.
- When a key conclusion is close to the threshold, run multiple seeds or repeat the run, and report variance or a bootstrapped CI.
- Don't compare using the "best post-train checkpoint" after the fact — compare results under a fixed budget and fixed selection rule, or report the training-curve AUC.

The SFT/RL recipe frozen here is a diagnostic instrument, used to compare the pre-mid and mid checkpoints — it does not represent the final production post-train recipe. If the recipe is adjusted in pursuit of better results, a new experiment_id should be registered, and the original mid-train conclusion should not be carried over directly.

| Comparison item | What to look at | Failure signal |
| --- | --- | --- |
| Convergence speed | Whether the target capability is reached faster under the same budget | Only faster for a particular seed |
| Final capability | Whether the target capability still holds after post-train | Improves on base, disappears after post-train |
| Reward behavior | Whether RL reduces reward hacking or improves verifiable-task performance | Verbose reasoning, opportunistic formatting, answer drift |
| Safety/style | Refusal boundaries, writing quality, long-answer quality | Safety regression, templating, mistaken refusals |
| Long context | Whether long tasks remain usable after post-train | Long-context capability gets overwritten by SFT |

A four-quadrant read:

| Result | Interpretation | Decision |
| --- | --- | --- |
| Base improves, post-train also improves | The most credible mid-train gain | Can become a scale-up candidate |
| Base improves, post-train doesn't | May be a base-eval false positive, or post-train overwrote the gain | Go back to data/eval, do not scale up directly |
| Base doesn't improve, post-train improves | May have improved trainability or interacted with SFT/RL | Repeat with multiple seeds and validate on real tasks |
| Base regresses, post-train improves | High-risk trade-off | Only continue if non-negotiable capabilities remain intact |

### 6.7 Scorecard: how to read evaluation results

Every candidate checkpoint should produce a one-page scorecard. It's an input the Eval DRI feeds into the gate — it does not replace the final go/no-go decision in section 4.6.

| Field | Content |
| --- | --- |
| `checkpoint_id` | Checkpoint hash, training step, token count, context length |
| `target_capability_delta` | Change in primary metrics, difficulty buckets, and private tasks |
| `base_regression_max_drawdown` | Maximum regression in non-negotiable capabilities and changes in low-scoring buckets |
| `private_holdout_result` | Usage and results of dev-private and sealed-private; final-blind should stay unused/reserved through Gate 5 or release, with a record of whether it's still untouched |
| `long_context_result` | Length buckets, real tasks, short-task regression, serving config |
| `post_train_readiness_result` | Paired protocol, seed, gain retention, variance |
| `contamination_status` | Results of exact/near-duplicate/embedding/manual checks |
| `known_regressions` | Known regressions, failure-sample clusters, manual-review conclusions |
| `recommended_action` | kill / retry / extend / promote |

If some metric's gain is unusually high, and private tasks, manual review, and neighboring evals don't support it, first assume contamination, format adaptation, or overfitting rather than declaring a capability breakthrough.

At a gate meeting, look first at a one-line red/yellow/green summary, then at the full scorecard:

| Status | Meaning | Meeting action |
| --- | --- | --- |
| Green | Target, guardrail, private holdout, and post-train readiness all point the same way, with a complete evidence trail | Can discuss extend/promote |
| Yellow | There's a gain, but variance, regression, contamination, post-train retention, or serving cost is still unclear | Assign an owner to fill the evidence gap; don't scale up |
| Red | Non-negotiable capability crossed the line, contamination/license unresolved, an incident wasn't attributed, or systematic post-train deterioration | Rollback/kill, or reopen with a new experiment_id |

## 7. Risk and incident-handling runbook

Chapter 7 is not a survey of failure modes — it's the incident-handling runbook for during training: any anomaly must be traceable to a symptom, an experiment ID, an affected checkpoint, a set of evidence paths, and a continue/rollback/kill decision.

### 7.0 How to use this chapter

Normal monitoring, the eval registry, and the gate mechanism live in Chapters 4-6; this chapter handles only anomalies. Once an anomaly is triggered, the on-call DRI should first freeze the scene, then do a 30-minute first-pass diagnosis, and finally make a provisional decision. Until attribution is complete, do not change data, learning rate, eval harness, or the post-train recipe within the same run.

Once an incident occurs, do three things first — don't touch the config yet:

| Step | Action | Output |
| --- | --- | --- |
| 1. Freeze the scene | Save the checkpoint, optimizer, data manifest, eval raw outputs, system metrics, and relevant commits | `incident_id` and evidence paths |
| 2. Determine the severity | Judge observation / alert / blocker, assign a 30-minute first-pass owner | A provisional stop/continue decision |
| 3. Layered isolation | Work through system replay, data-manifest diff, eval-harness diff, and model-checkpoint diff in turn | A root cause, or an "unresolved" flag |

Log incidents into six categories first:

| Incident type | Typical scope |
| --- | --- |
| numerical | NaN, Inf, loss explosion, abnormal gradients, mixed-precision overflow |
| data | Data-bucket contamination, format drift, license issues, synthetic-data templating, wrong sampling weights |
| eval | Abnormal scores caused by the harness, prompt, judge, metric, sampling, or contamination |
| infra | Throughput, GPU utilization, NCCL, storage, checkpoint, or serving-config anomalies |
| capability | Target capability not improving, general-capability regression, guardrail worsening, real-task long-context regression |
| post-train handoff | Gains disappear after SFT/RL handoff, increased reward hacking, recipe noise amplification |

Hard rule: any capability conclusion or training-effect conclusion must first complete four layers of isolation — system replay, data-manifest diff, eval-harness diff, and model-checkpoint diff; if a given layer is irrelevant to the incident, it should be marked `N/A` with a stated reason. If the evidence is incomplete, it can only be logged as an unattributed incident — it cannot be written up as a capability conclusion.

### 7.1 Incident severity: observation, alert, blocker

| Level | Trigger signal | On-the-spot action | Can training continue |
| --- | --- | --- | --- |
| Observation | Minor fluctuation in a single eval, slight shift in bucket loss, a single seed near a threshold | Log an incident_id, re-run neighboring checkpoints or the fixed sample basket | Can continue, but no promotion |
| Alert | Consecutive checkpoints show abnormal metrics, public/private divergence, one data bucket's loss clearly deviating, target capability up but guardrail worsening | Freeze variables, pull in Data/Eval/Training DRIs for a 30-minute first pass | Depends on the guardrail; scale-up is usually paused |
| Blocker | NaN/Inf, discontinuous resume, unresolved contamination or license issue, non-negotiable capability crossing the line, usable offline but unservable online | Stop the run or stop the release, roll back to the most recent healthy checkpoint, open an incident review | Do not continue, unless a new experiment_id is created after the review |

Handling principles:

| Principle | Concrete practice |
| --- | --- |
| Freeze the scene first | Save the checkpoint, optimizer state, training logs, data manifest, eval raw outputs, system metrics, and relevant commits |
| Attribute in layers first | Determine which layer changed first — system, data, eval, model, or post-train recipe |
| Check the buckets first | Normal global loss doesn't mean every data bucket, language, length, and task is normal |
| Protect the guardrail first | If a non-negotiable capability's regression exceeds the threshold, don't wait for the target capability to keep improving |
| No silent patching | Changing filters, sampling weights, prompts, harness, judge, decoding, or serving config always requires a new experiment_id |

### 7.2 In-training incident triage table

| Incident type | On-the-spot symptom | 30-minute first pass | Layered attribution | Immediate decision | Must be logged |
| --- | --- | --- | --- | --- | --- |
| numerical | NaN / Inf / loss explosion | Gradient norm, overflow count, LR/warmup, most recent batch, optimizer state, resume log | system: precision/kernel; data: bad sample; model: LR/clip; checkpoint: resume | Blocker; roll back to the most recent healthy checkpoint, replay the problem batch | checkpoint_id, batch id, overflow log, optimizer hash, replay result |
| numerical / model | Loss spike after a stage transition | Stage-transition commit, LR schedule, mix weights, length distribution, whether optimizer/RNG is continuous | data: sudden mix change; model: schedule; system: resume; eval: window definition | Observation if the spike is explainable and recovers quickly; rollback if it persists | phase-change diff, curves from the preceding 3 checkpoints, data-manifest diff |
| infra | Drop in throughput / abnormal GPU utilization | tokens/s, MFU, dataloader wait, NCCL, storage IO, kernel version, batch shape | System first; don't attribute to model change before confirming | Pause capability conclusions; stop the run to investigate if needed | System metrics, profile trace, code/image version, rerun comparison |
| data | Global loss normal but one bucket's loss abnormal | Bucket validation loss, sampling weight, tokenizer/packing, manifest diff, sample spot check | Data first; then check tokenizer/packing and eval bucket | Freeze or drop the problem bucket; rollback the manifest if severe | bucket id, manifest hash, sample examples, filter version, fix diff |
| data / capability | Synthetic data templating or rising error rate | Teacher/version, prompt, verifier, template n-gram, response length, human error rate | data: generator; eval: sample set too narrow; model: learned the format, not the capability | Lower the synthetic ratio or isolate the bucket; don't write a format gain up as a reasoning gain | generator config, verifier version, repetition rate, manual-review record |
| capability | Sharp early regression in general capability | Base-regression max drawdown, low-scoring bucket, fixed language/domain basket, data mix | model: LR/trained too long; data: specialized share too high; eval: sampling bias | Trip the guardrail; roll back or lower the specialized share | scorecard, failure-sample cluster, mix curve, rollback point |
| capability | Target capability improves but guardrail worsens | Target metric, non-negotiable capabilities, neighboring checkpoint, error-type shift | model/data trade-off; confirm it isn't an eval-definition change | No promotion; extend only if the trade-off is accepted by the business and reproducible | Pareto curve, guardrail thresholds, DRI sign-off, sample comparison |
| eval | Sudden jump/drop in an eval | data_hash, harness_commit, prompt/wrapper, judge, decoding, answer extractor | eval first; run the old/new harness diff on the same checkpoint | Freeze the capability conclusion; cross-run old/new harness | eval diff, raw outputs, judge version, metric change note |
| eval / data | Public benchmark improves but private doesn't | Contamination report, private holdout, question-type similarity, raw output | Data contamination or eval overfitting; could also mean public set is too narrow | Downweight from primary metrics; do not scale up | Contamination evidence, holdout usage log, excluded-sample list |
| capability / context | Needle looks good but real long tasks are poor | Long-task raw output, evidence position, information density, unanswerable samples, length distribution | eval: needle too narrow; data: missing synthesis/conflict tasks; system: serving difference | Don't use needle as the primary gate; pause scaling long training | Long-task failure cluster, evidence localization, length-bucket scores, serving config |
| capability / context | Long-context training hurts short tasks | sequence_length_distribution, short-task regression, packing/padding, short-sample share | data: long samples diluting; model: side effect of position/attention adaptation | Roll back the length mix or restore the short-sample ratio | Length-distribution diff, short-task scorecard, curriculum version |
| infra / context | Usable offline but not online for long context | Serving config, KV cache, chunked prefill, batching, kernel, latency/cost | System first; defer the model-capability conclusion | System blocker; do not release, don't record an online failure as a model failure | Offline/online config diff, online raw output, profile |
| post-train handoff | Gains disappear after post-train | Paired protocol, seed, SFT/RL data version, checkpoint selection, training-curve AUC | Post-train recipe issue or base-eval false positive; could also be mid-train instability | Don't scale up; repeat the paired run or go back to the target data | Recipe hash, seed, A/B curve, post-train raw outputs |
| post-train handoff | Increased reward hacking | RL raw output, reward/verifier, refusal/safety, format dependence, CoT templating | Post-train reward loophole; mid-train may have prematurely locked in the format | Lower behavioral-format data share; fix reward/verifier and rerun | Reward version, hacking samples, behavioral-data share, fix record |
| infra | Checkpoint resume discontinuity | Loss before/after resume, optimizer/RNG, data cursor, checkpoint hash, training code version | System/checkpoint first; check data/model after ruling those out | Rollback; open a new run once a replay resume test passes | Checkpoint lineage, RNG/data cursor, replay log, code hash |
| eval | Conclusion flip-flops between checkpoints | Neighboring checkpoint, CI/variance, multiple seeds, selection policy, raw outputs | Eval noise or selection bias; genuine model fluctuation needs a second check | Don't decide from a single point; report the curve, not the best point | Selection policy, full curve, confidence interval, failure samples |

### 7.3 Data-incident runbook

The first principle for a data incident is to isolate the version, not patch the live setup. Any change to filters, generators, dedup, sampling weights, tokenizer, or packing must produce a new data_version and manifest hash.

| Step | Action | Exit condition |
| --- | --- | --- |
| 1. Freeze | Save the old manifest, sampling weights, generator config, filter version, and sample examples | Able to reproduce the input that caused the incident |
| 2. Diff | Compare token counts, language/domain/length distribution, duplication rate, contamination rate, bad-sample rate | Explains at least one abnormal bucket |
| 3. Isolate | Drop or downweight the problem bucket, keep the general-fidelity bucket and guardrail evals | The problem bucket no longer enters continued training |
| 4. Rerun | Rerun data validation and linked eval with a fixed checkpoint | Proves the fix came from the data, not a redefined eval |
| 5. Review | Update the data-bucket admission card and the prevention_rule | Only the new data_version can enter the next training run |

If contamination, license, or a privacy boundary can't be fully explained, that data version should simply be killed. For mid-train, "possibly contaminated but scores well" is not an acceptable state.

### 7.4 Training-incident runbook

A training incident should first protect recoverability. After discovering a numerical or resume-type problem, don't tweak the learning rate hoping to get lucky — first confirm whether the checkpoint, optimizer, RNG, data cursor, and code version can be replayed.

| Step | Action | Exit condition |
| --- | --- | --- |
| 1. Stop the clock | Mark an incident_id, freeze the current run, stop writing capability conclusions | The on-the-spot log and state are complete |
| 2. Replay | Replay a short window from the most recent healthy checkpoint, confirm reproducibility | Reproducible means it can be localized; not reproducible means logging system uncertainty |
| 3. Single-variable fix | Change only one variable at a time: LR, clip, precision, bad batch, or resume logic | The fix can be attributed to a metric change |
| 4. Regression | Rerun the per-bucket loss, base regression, and key target eval | No new guardrail incident appears |
| 5. Decide | kill / retry / rollback / extend / promote | With DRI sign-off and an evidence path |

The minimum condition for training to continue: numerical stability, successful system replay, no drift in the data manifest, and no drift in the eval harness. If any one is missing, only retry or rollback is allowed — no promotion.

### 7.5 Evaluation-incident runbook

The most common evaluation-incident mistake is treating a tool change as a capability change. As long as any one of the prompt, wrapper, judge, answer extractor, decoding, sample set, or metric changes, the old and new scores cannot be compared directly.

| Investigation matrix | Old checkpoint | New checkpoint |
| --- | --- | --- |
| Old harness | Reproduces the historical baseline | Shows the model's real delta |
| New harness | Shows the change in tooling definition | Only usable as a new-definition result |

Only when "the new checkpoint improves under the old harness" and "the old checkpoint doesn't improve equally under the new harness" both hold can the gain be tentatively attributed to the model. If private holdout has been repeatedly viewed or tuned against, it should be downgraded to dev-private, and a new sealed-private or final-blind set should be established.

### 7.6 Post-train-handoff incidents

If mid-train's gain disappears after post-train, don't simply conclude that mid-train was useless. Four things need to be checked at once:

| Item to check | Possible problem | Handling |
| --- | --- | --- |
| Is the recipe frozen | Changes in SFT/RL data, seed, budget, reward/verifier, decoding | Rerun the paired protocol |
| Is selection biased | Only the best post-train point or the best base point was picked | Use a fixed checkpoint-selection policy |
| Was the capability overwritten | SFT style data overwhelms the target capability, RL reward biases toward short answers or format | If post-train data/reward is adjusted, register a new experiment_id or paired_protocol_version before retesting readiness |
| Is the gain a false positive | Base-eval contamination, public overfitting, too narrow a sample set | Return to the eval registry in Chapter 6 and section 7.5 |

If the post-train handoff fails under the paired protocol for two consecutive rounds, and the base-side gain exists only on public benchmarks or a single seed, kill that mid-train direction; if the base-side gain is stable but gets overwritten by SFT/RL, write the conclusion as "post-train handoff not yet achieved," not "mid-train produced no gain." When adjusting SFT/RL data, reward, verifier, budget, or seed to investigate the overwrite issue, the old paired protocol's conclusion can no longer serve as evidence of a mid-train gain — it can only serve as a diagnostic clue.

### 7.7 Incident post-mortem template

Every alert- or blocker-level incident needs a post-mortem record. A post-mortem is not a blame document — it's meant to help the next training run avoid the same pitfall.

```text
incident_id:
experiment_id:
incident_type: numerical | data | eval | infra | capability | post-train handoff
severity: observation | alert | blocker
first_detected_at:
affected_checkpoint:
symptom:
root_cause: confirmed | suspected | unresolved
changed_variables:
rollback_point:
evidence_paths:
four_layer_isolation:
  system_replay:
  data_manifest_diff:
  eval_harness_diff:
  model_checkpoint_diff:

```

If `root_cause` is still `unresolved`, the incident can close the training action, but it cannot close the epistemic conclusion: the documentation can only say "unattributed incident, isolated" — it must not say "model capability regressed" or "some data bucket was effective."

## 8. A 90-day roadmap for new teams

This roadmap is a reference cadence, not a calendar commitment. Moving to the next stage should be decided by Gates 0-5, not by which day it is.

### 8.0 Gate dashboard: each stage answers only one decision question

The purpose of the 90-day roadmap is not scheduling — it's moving the project from "we want to train" to "we have enough evidence to train." Each gate answers only one question:

| Gate | Decision question | Required evidence | Blocker | Owner | Next action |
| --- | --- | --- | --- | --- | --- | --- |
| Gate 0 | Does this goal actually require mid-train | Charter, non-negotiable capabilities, v1 eval registry, v1 post-train paired protocol | The goal can be solved by SFT/RAG/product logic; eval or holdout not frozen | Model Lead | go / no-go on the charter |
| Gate 1 | Can the data enter experiments | Data manifest/hash, license, contamination check, sample review, linked eval | Data source unclear, synthetic generator has seen the eval, holdout leakage | Data DRI | Data readiness memo |
| Gate 2 | Did proxy ablation rule out bad directions | Target gain, general regression, signal from two scales or a target short run, failure-sample cluster | Only public benchmarks improve; synthetic data is templated; proxy conclusion is unstable | Eval DRI | Ablation decision memo |
| Gate 3 | Is the main-model short run worth continuing | Checkpoint curves, per-bucket loss, scorecard, incident log, Pareto result | NaN/loss spike, discontinuous resume, guardrail crossed, long context hurting short tasks | Training Infra DRI | extend / rollback / kill |
| Gate 4 | Can the gain be retained by post-train | Paired SFT/RL result, seed, AUC, raw outputs, reward/safety regression | Improves on base but disappears after post-train; recipe changed mid-run; increased reward hacking | Post-train DRI | Readiness report |
| Gate 5 | Scale up training, or shrink and redo | Go/no-go memo, model registry, rollback checkpoint, cost-benefit judgment | Gain traces to contamination/narrow eval/single seed; incident unattributed; can't explain the regression | Decision owner | scale / shrink / stop |

Whenever a gate's evidence is incomplete, don't bypass it with "let's train a bit more and see." Mid-train projects are expensive — the real pacing control comes from the gates, not the calendar.

Every gate's dashboard record must also include `status`, `owner`, `evidence_path`, `version_hash`, `stale_after`, and `next_action`. A green status without an evidence path should be treated as yellow.

### Day 0-14: define the goal and evaluation

Corresponds to Gate 0, primarily owned by the Model Lead, Eval DRI, and Post-train DRI; the decision meeting in this stage answers only one question — does this goal actually require mid-train.

Deliverables:

- Mid-train charter: target capability, non-negotiable capabilities, target checkpoint, budget.
- Eval matrix: base eval, capability eval, long-context eval, post-train readiness.
- Data-bucket design document.
- Risk list and go/no-go gate.
- Frozen post-train recipe: SFT/RL data version, training budget, seed, harness, eval sets, failure criteria.

Go/no-go:

- If the eval registry, private holdout, and post-train handoff recipe haven't been frozen, don't enter training.
- If a private holdout's creation time is later than the training data mix, or if tuning against private holdout is allowed, don't enter training.

### Day 15-35: data and small-model ablation

Corresponds to Gates 1-2, primarily owned by the Data DRI and Eval DRI; every experiment must be logged in the ledger from section 4.6.

Deliverables:

- Data-mix experiments on, e.g., 1B/3B/7B proxy models; the exact scale depends on the team's existing model lineage and budget.
- Learning-rate and token-budget sweeps.
- A correctness and diversity report for synthetic data.
- A loss-versus-capability correlation analysis for each data bucket.
- Data manifest/hash, near-duplicate detection report, contamination-check report, manually reviewed samples.

Go/no-go:

- At least one mix shows a target-capability improvement with an acceptable general-capability regression.
- Synthetic data shows no obvious contamination or style collapse.
- Proxy success only shows that a bad direction has been ruled out — it does not prove the target scale will necessarily work; before the main-model short run, at least two scales must point the same way, or a target-model short run must confirm the key signal.

### Day 36-60: main-model short-run mid-train

Corresponds to Gate 3, primarily owned by the Training Infra DRI, Eval DRI, and Model Lead; a kill switch must be defined before training launches.

Deliverables:

- A main-model short run, e.g. in the 10B-100B token range; the exact token budget is decided by the Gate 2 evidence and training cost.
- Daily checkpoint evaluation.
- A capability/forgetting Pareto curve.
- Selection of a candidate checkpoint.
- Training runbook, checkpoint lineage, resume records, training-code commit, incident log.

Go/no-go:

- The target-capability gain isn't driven by a single benchmark.
- The general-capability decline is below a pre-defined threshold.
- No obvious style drift in generated samples.
- Training is stopped or rolled back if NaN, an unrecoverable loss spike, abnormal gradients, abnormal throughput, an abnormal loss in some data bucket, discontinuous checkpoint resume, or long-context training hurting short tasks occurs.

### Day 61-75: post-train handoff validation

Corresponds to Gate 4, primarily owned by the Post-train DRI and Eval DRI; if the post-train recipe changes during this stage, the mid-train conclusion should be treated as invalid or re-tagged with a new experiment ID.

Deliverables:

- A fixed-SFT-recipe comparison.
- A fixed RL/RLVR-recipe comparison, if applicable.
- Post-train real-task evaluation.
- A reward-hacking / safety / style regression report.
- Post-train readiness report: recipe version, seed, budget, harness, failure criteria, and gain-retention ratio.

Go/no-go:

- The mid-trained checkpoint still retains its gain after post-train.
- Alignment difficulty has not increased significantly.

### Day 76-90: scale-up or shrink decision

Corresponds to Gate 5, primarily owned by the Decision owner, Model Lead, and Release owner; this stage is not automatic scale-up — it's a decision to continue, shrink, redo the data, or stop.

Deliverables:

- A scale-up candidate recipe, or a shrink/redo recipe for the next stage.
- A decision on whether to move into 100B-1T+ token training.
- A list of data- and eval-automation improvements.
- A next-stage plan for long context or a second capability target.
- Model registry: checkpoint lineage, data manifest, eval raw outputs, training logs, permissions, retention period, and a rollback-capable checkpoint.

Go/no-go:

- If the gain mainly comes from contamination, a narrow eval, or post-train chance, do not scale up.
- If the gain is stable, explainable, and survives post-train, move into main training.

## 10. Special reminders for foundation model teams with post-train experience

First, don't approach mid-train with an SFT mindset. Mid-train data can include QA, CoT, and code tasks, but its goal is not to have the model learn the product's answer format — it's to change the capability distribution.

Second, don't make RL take the blame for everything. If the base model lacks a sufficient substrate in math, code, long context, and self-correction, RL will likely just learn superficial search or verbose reasoning.

Third, don't chase leaderboards alone. Mid-train's real gain must hold up simultaneously on private tasks, real product tasks, and through the post-train handoff.

Fourth, don't chase 1M context from the start. For most teams, making 32K/128K reliable first is more practical than demonstrating an extremely long context.

Fifth, don't neglect data engineering. In mid-train projects, the training code is often not the bottleneck — data lineage, contamination control, bucketed eval, and experimental discipline are.

## 11. First-round search space: example search grid, not a default mix

This chapter is a worked example, not a recipe. Its purpose is to help a team doing mid-train for the first time string data, training, evaluation, and the post-train handoff into a minimal evidence chain.

If a team already has a usable base model and a stable post-train pipeline, it's advisable for the first round to not go broad and comprehensive, but instead build a minimal closed loop of "capability mid-train + post-train handoff." The ratios below are not a recommended recipe — they are a search space for launching ablations; different model scales, pretraining histories, target languages, and product tasks will significantly change the optimal mix, and it must be validated through proxy scale and a main-model short run before main training.

The "minimal closed loop" here is not a minimal training recipe — it's about validating, at the smallest possible experimental cost, whether data, training, evaluation, and the post-train handoff can form an interpretable conclusion. The ratios and token ranges below are only for designing ablation variables — they must not be used as a default mix, default LR, or default budget.

These ranges can only be used as ablation variables once the base checkpoint, target capability, non-negotiable capabilities, eval registry, data manifest, and post-train paired protocol have all been frozen; otherwise they should not enter the training configuration.

Goal:

- Improve math, code, STEM, and complex QA.
- Don't significantly harm general capability, multilinguality, factuality, or natural generation.
- Validate whether the gain survives SFT/RL.

Data-mix search space (bucket-sensitivity sweep axes):

- High-quality general text: test the fidelity floor at low/mid/high points, e.g. 30/50/70% — not a fixed-proportion recommendation.
- Code and FIM: test code capability and drift in ordinary generation at low/mid/high points, e.g. 10/20/30%.
- Math/STEM: test the reasoning-injection gain, saturation point, and general regression at low/mid/high points.
- Synthetic textbook/verifiable reasoning: sweep the cap to test verifier quality, templating, and amplified teacher errors.
- QA/CoT/short-answer task forms: use an isolated toggle or low-proportion mix to test format drift, avoiding prematurely locking in post-train behavioral formats.

These bucket axes are only for first-round single- or few-variable search — they are not a normalized ratio table meant to be satisfied all at once. The actual mix must be decided through small-model and main-model short-run experiments.

This starting point is not a copy of OLMo 2's, Qwen3's, Llama 3's, or Phi-4's recipe, nor is it the optimal ratio reverse-engineered from public reports. It's just a search grid designed to help a new team expose data conflicts, forgetting risk, and synthetic-data boundaries.

Before main training there must be a mix-sensitivity curve, not just a single point that looks best. At minimum, answer:

- As the general-data proportion decreases, which non-negotiable capabilities regress first?
- As the math/STEM or code proportion increases, is the gain linear, saturating, or reversing?
- As the synthetic ratio increases, do private tasks, style review, and template-repetition rate deteriorate together?
- Does the same mix point in the same direction across different seeds or neighboring checkpoints?
- Is the target-capability gain enough to offset the general regression and the training cost?

The first round should not run just one mix. It's better to keep a control mix and build a small matrix around a single variable:

| Variant | What changes | What stays the same | Purpose |
| --- | --- | --- | --- |
| Control | Low-risk general-fidelity mix | LR, token budget, context length | Establish a regression baseline |
| Math/STEM up | Only increase math/STEM | Code, general, LR unchanged | Judge the reasoning-injection gain and the forgetting cost |
| Code/FIM up | Only increase code/FIM | Math, general, LR unchanged | Judge code capability and drift in ordinary generation |
| Synthetic cap | Cap the synthetic proportion | Other buckets unchanged | Judge whether synthetic data causes templating |
| General retain | Increase high-quality general data | Target buckets unchanged | Judge whether general fidelity reduces regression |
| LR lower | Only lower the LR | Data mix unchanged | Separate a data problem from an optimization problem |

Each variant should change only 1-2 primary variables. Changing the mix, filter, LR, or eval version mid-run makes the experiment impossible to interpret.

Starting point for a main-model short run after passing Gate 2:

- Continue training at a low learning rate.
- Use the original context length or a small extension.
- An example upper bound of a 10B-50B-token-scale short-run main-model validation; the actual budget must be jointly decided by the proxy results, the target-model short-run signal, the forgetting threshold, and cost.
- Save and evaluate a checkpoint every 10%-20% of tokens.

Starting point for evaluation:

- Base eval: MMLU/MMLU-Pro, BBH, GPQA, GSM8K/MATH, HumanEval/MBPP, multilingual sets.
- Private eval: internal math, code, complex QA, real user tasks.
- Post-train readiness: a fixed SFT recipe, comparing the pre-mid and mid checkpoints.

If this round of the loop shows no stable gain, don't rush to expand the token budget. Go back to the data and the learning rate first.

## 12. Source map

This chapter is not an endnote-style bibliography — it's a route map for readers to double-check this piece's conclusions. It's advisable for a team to read sources in three tiers: first read the primary reports to confirm factual boundaries, then read surveys to build taxonomy, and finally read controlled experiments to form internal ablation hypotheses.

### 12.1 Primary technical reports: the factual bedrock

| Source | What to check in the original first | How this piece uses it | What cannot be concluded |
| --- | --- | --- | --- |
| OLMo 2 Technical Report: <https://arxiv.org/abs/2501.00656> | The report explicitly uses a mid-training layering, and discloses the data mixture, mid-training, post-training, and open artifacts | The public paradigm for narrow-sense mid-training; naming stages, data lineage, and a transparent experiment ledger | Cannot conclude that OLMo 2's data ratios suit Chinese, multilingual, agentic coding, or a closed-source production model |
| Qwen3 Technical Report: <https://arxiv.org/abs/2505.09388> | Three pre-training stages: general knowledge, STEM/code/reasoning enhancement, long context; plus inference extrapolation/deployment techniques | Engineering-wise classified as a mid-train-like case of capability shaping + context adaptation | Cannot rename Qwen3's original report as mid-training, nor reverse-engineer its full data ratios |
| DeepSeek-V3 Technical Report: <https://arxiv.org/abs/2412.19437> | 14.8T-token pretraining, 32K/128K context extension, and architecture/training co-design such as MLA/MoE/MTP | Shows long-context extension must be viewed together with architecture, systems, and training stability | Cannot isolate context extension into an ordinary continued-training data recipe |
| Phi-4 Technical Report: <https://arxiv.org/abs/2412.08905> | Synthetic data for pretraining and midtraining; midtraining extends context from 4K to 16K over roughly 250B tokens | Shows synthetic data can be central to a training strategy, while also noting the explicit midtraining stage mainly handles context expansion | Cannot reduce Phi-4 to "reasoning mid-train relying purely on synthetic CoT," nor precisely attribute the contribution of each part |
| Qwen2.5-1M Technical Report: <https://arxiv.org/abs/2501.15383> | Progressive long-context pre-training to 256K, long-context post-training, DCA/YaRN extrapolation, and sparse-attention/chunked-prefill deployment optimization | Separates the boundaries between training scale-up, 1M inference extrapolation, and deployment optimization | Cannot write up 1M context as "directly mid-trained to 1M," nor claim training doesn't matter |
| The Llama 3 Herd of Models: <https://arxiv.org/abs/2407.21783> | 405B's initial pre-training over roughly 15.6T tokens; long-context pre-training over roughly 800B tokens to 128K; a final 40M-token annealing | A conservative reference: continued pre-training, long context, and annealing should be broken into observable stages | Cannot equate Llama 3's continued pre-training directly with its own naming of mid-training, nor transplant it as a small team's default budget |

| Source | Main use | Usage boundary |
| --- | --- | --- |

### 12.4 Recommended reading order

1. Read OLMo 2 first: understand how documentation, data, checkpoints, and post-training layer together when mid-training is treated as an independent stage.
2. Then read Qwen3: understand the "general -> capability enhancement -> long context" stage design, while noting the original report calls these pre-training stages.
3. Then read DeepSeek-V3 and Qwen2.5-1M: understand that long-context extension cannot be separated from architecture, inference extrapolation, and the serving system.
4. Then read Phi-4: understand the value and the boundary of synthetic data, being careful not to reduce the synthetic-heavy strategy to a single reasoning mid-train.
5. Then read Llama 3: understand the conservative path of continued pre-training, long-context pre-training, and annealing.
6. Finally read the survey, PRISM, and pre/mid/RL papers: turn mechanistic hypotheses into the team's own ablations, rather than writing paper conclusions directly into a training decision.
